# 刷卡取件（拉式打印 / pull printing）

给**企业内网**用的模式：员工在自己电脑上提交打印，任务先**暂存**在服务器上；
走到打印机旁刷工牌，任务才真正送去打印。

> 🧰 **去现场装机器的人看 [刷卡取件终端部署手册.md](刷卡取件终端部署手册.md)** ——
> 那篇是照着从第一条做到最后一条的部署手册（买读卡器前的卡型验证、从本机
> 复制到终端机器、装依赖写配置、自检、开机自启、绑卡、验收、排障）。
> 本文讲的是**为什么这么设计**。

与便利店那套扫码自助打印是**两个不同的部署形态**，不只是"收不收钱"的差别：

|            | 扫码打印（原形态）        | 刷卡取件（本文）               |
| ---------- | ------------------------- | ------------------------------ |
| 打印发生在 | 提交的那一刻              | **刷卡的那一刻**         |
| 身份从哪来 | 支付宝授权登录 / 访客账号 | 公司账号 +**NFC 工牌**   |
| 计费       | 核心                      | 没有，而且**与计费互斥** |

## 三个开关两两互斥

`billing_enabled` / `pull_mode_enabled` / `guest_mode` 都在回答同一个问题
——「**谁是这个部署的打印入口**」——两两都不兼容：

| 组合         | 为什么不行                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 计费 × 取件 | 一个要求先付钱、一个压根不收费；`/api/print` 会同时「该 403」又「该暂存」                                                    |
| 取件 × 访客 | 访客是所有人共用的一个账号，而取件模式的**全部意义就是「任务认人」**。共用账号下所有人的任务会混在一起，刷卡时统统打出来 |
| 计费 × 访客 | 已有约束：公摊钱包，花光无法追责                                                                                               |

互斥在 `adminUpdateSettingsHandler`（取件那一侧）与 `adminUpdatePricesHandler`
（计费那一侧）**两个方向各校验一次**。只做一边的话，从另一个入口进来就能撞上。

## 复用了「先提交、后送印」那套机器

这个仓库本来就有一整套推迟打印的机制 —— 计费订单。取件模式没有另起炉灶：

```
计费：pending_payment ──(付款)──► paid ──(ClaimOrderForPrint)──► printing
取件：held ──────────────────── (刷卡) ─────────────────────► printing
```

- 转换流水线（`prepareOrderPrint`）、参数快照、送印（`startPrintForOrder`
  的孪生兄弟 `startPullPrintForOrder`）、结果核对（`confirmPrintResults` /
  `decidePrintAction`）**全部复用**。
- 取件订单的计费列一律为 0（`createOneOrder` 的 `Hold` 分支）。
- 释放到哪台 = **提交时选的那台**（`print_orders.printer_uri` 是硬约束）。
  换来的是参数绝不会与目标机不匹配（A3、进纸盒、双面都真实存在）。
  若将来要改成「任意一台都能取」，代价只是放弃进纸盒选择（强制
  `media_source=auto`）——**数据模型不用动**。

### 为什么不新开一张表

`prepareOrderPrint` 这条流水线在仓库里被标为「四胞胎」复制，另起一张表要么
再造一份流水线、要么强行抽象合并 —— 在无集成测试网的情况下是纯回归风险。
更要命的是：`maintenance` 的**文件保护逻辑完全长在 `print_orders` 上**，
另起表必然漏保护，而那种漏的表现是「员工刷卡时文件不见了」，根因却在一小时前。

## 🚨 必须守住的不变量

### 1. `held` 必须在 `ListActiveOrderFiles` 的保护名单里

**这是整个功能最容易出人命、也最容易被漏掉的地方。**

`maintenance` 每小时按 `print_jobs` 的保留期删文件，它**完全不知道订单的存在**，
只认 `ListActiveOrderFiles`（`internal/store/orders.go`）给的那份名单。
名单里少了 `held` 的表现是：**员工刷卡时提示「待打印文件缺失」** ——
而根因是一小时前的一次例行清理。

`internal/store/pull_test.go` 的 `TestListActiveOrderFilesIncludesHeld` 盯着它，
而且验证过「把 `held` 去掉它真的会红」。改那个 `IN` 列表之前先看这条测试。

### 2. ⚠️ 别被两处死代码骗了

```
$ grep -rn "OrderStatusesActive" --include=*.go .
./internal/store/orders.go:28:var OrderStatusesActive = []string{     ← 全仓无引用
```

- **`OrderStatusesActive` 是死代码**（本次已删除）。它自称「仍在占用文件的状态
  集合」，但没人读它。真正保护文件的是上面那条硬编码的 `IN` 列表。
  照着它加状态会以为保护到位了，**实际文件照样被删**。
- **`ListStalePrintingOrders` 也曾经是死代码**（本次改成了 `ListOrphanPullOrders`）。
  见下面「孤儿恢复」。

### 3. 释放失败**绝不走退款路径**

`failOrderAndRefund` 会把订单标成 `failed` 并尝试退款。取件订单金额恒为 0，
所以它不会真的退钱（`order_print.go` 里那句 `if order.AmountCents <= 0 { return nil }`）
—— **但它在那之前就已经把订单标成 failed 了**，员工的任务照样丢。

🚫 别拿「金额为 0 所以无害」当理由偷懒。取件走的是另外两个函数：
`revertPullOrder`（退回待取件）与 `failPullOrder`（标失败，不退款）。

## 释放流程

`POST /api/kiosk/release`，body `{"token": "...", "cardNo": "..."}`。

```
① 认终端   token → kiosk_terminals → printer_uri（不认识 / 已停用，分别报）
② 认卡     cardNo → users.card_no  → 用户（查不到 → card_unbound）
③ 打印机预检 printerUnavailableReason()  ── 不可用就【一个字都不改库】
④ 原子领取 UPDATE ... WHERE user_id=? AND printer_uri=? AND status='held'
⑤ 逐个送印 事务外（IPP 是网络调用），失败退回 held
```

### 「刷一次只打一次」

根基全在 ④ 的 `WHERE status='held'`：

- 第二次刷卡匹配 0 行。
- 两台终端并发时行级锁会串行化，每行只有一个 `UPDATE` 拿到。
- **多实例部署同样安全** —— 这里不依赖任何进程内的锁
  （对比：`wallet_refund.go` 的 `userRefundLock` 是进程内 mutex，那种才有多实例隐患）。

### 失败时退回 `held`，不是 `failed`

员工没付钱，任务不该丢。退回 `held` 可以原地重刷、可以等打印机恢复、
到期还有 TTL 兜底 —— 失败语义**完全可逆**。

唯一的例外是**文件缺失**：重刷多少次都一样，那是死循环，所以标失败。

### 送印成功之后的失败：扫码取件没有「退款」这一说

任务进了 `printing` 且有 `job_id` 之后，由现有核对链路接管。
`reconcilePrintingOrder` 里对 `source='pull'` 的订单做一次**动作翻译**
（`pullReconcileAction`）：

| 计费的裁决                  | 取件的动作                                                        |
| --------------------------- | ----------------------------------------------------------------- |
| `printActionRefunded`     | `printActionPullFailed` —— 标失败，不退款                     |
| `printActionCancelRefund` | `printActionPullCancelFailed` —— 先取消任务，再标失败，不退款 |
| 等待 / 完成 / 转人工 / 未知 | 原样透传（与钱无关，两边行为本来就该一样）                        |

🚫 **不要在 `decidePrintAction` 里加分支**：它被 `order_worker_test.go` 逐分支
覆盖，是全系统唯一决定「已付的钱要不要退」的地方，语义不该被另一种模式污染。
翻译放在它外面。

**这里不退回 `held`**：任务已被 CUPS 收下，纸有没有出来**存疑**。
自动退回重打有**重复出纸**风险 —— 那比「让员工重新提交一次」糟得多。

### 孤儿恢复

释放流程是「先领取（held→printing），再在事务外送印」。进程若恰好在两步之间
挂掉，订单会永远停在 `printing` 且没有 `job_id`；而核对链路只捞 `job_id` 非空的，
**这类孤儿没有任何回收路径**。

`recoverOrphanPullOrders` 每 30 秒扫一次，把它退回 `held`。

⚠️ **判据是 `error = PullClaimMarker`，不能退化成「`job_id` 为空」**：
「送印成功但任务号回写失败」的订单形状一模一样，回退它会让员工下次刷卡
**重复出纸**。带标记之后只有「领了但 IPP 请求还没发出去」才匹配。

## 工牌号

### 存的是**卡的 UID**，不是卡面印的号

⚠️ 这是最容易被误会的一点：**UID 与卡面上印的数字通常是两回事**。UID 是芯片
出厂固化的唯一标识（如 `04A23B1C`），而卡面印的往往是公司自己编的工号。
两者不一样是**正常的，不是读错了**。

### 归一规则是对称的

绑定与刷卡**两侧都过 `store.NormalizeCardNo`**：去掉空白与 `:` `-` `_`、转大写。

对称是关键 —— 只要两侧规则一致，归一就不会把两张不同的卡弄成一张；
而它解决的差异是**必然会发生**的：

| 差异   | 为什么必然发生                                                                                        |
| ------ | ----------------------------------------------------------------------------------------------------- |
| 大小写 | PC/SC 读卡器吐十六进制 UID，管理员把它从终端抄进管理界面时，`04A23B1C` 写成 `04a23b1c` 迟早会发生 |
| 分隔符 | 同一个 UID 各家写法不同：`04:A2:3B:1C` / `04-A2-3B-1C` / `04A23B1C`                             |

🚫 **不**去前导零、不删数字 —— 那会改变卡的身份。

🚫 归一也**救不了**「两台不同型号读卡器读出不同 UID」：那是物理层差异
（Wiegand 格式号 vs 卡面号、字节序不同、ID 卡 125kHz vs IC 卡 13.56MHz）。
只能靠**统一读卡器型号**，换型号就要重新绑一遍卡。

### 绑定：两条路

**浏览器访问不到 PC/SC 读卡器** —— 所以「点按钮」和「刷卡」天生是两个地方，
中间必须由服务端记一笔（绑定窗口）。但**读卡器插在哪台机器上没有关系**：

> UID 是芯片固化的。同一个读卡器插在管理员电脑上、还是插在打印机旁的树莓派上，
> 读同一张卡得到的字符串**完全一样**（这正是 PC/SC 相比键盘模拟读卡器的好处）。
> **所以绑卡不必走到打印机那边去。**

推荐做法：给管理员电脑配一台 `printer_uri = ''` 的**仅用于绑卡终端**
（管理界面新建终端时勾「仅用于绑卡」），读卡器插在工位上，绑卡全程不离开座位。
这种终端在没有等待中的窗口时会明确回一句「请先在管理界面点开始等待刷卡」，
而不是含糊的「没有待取件任务」。

#### 路一：刷卡绑定（推荐，单个绑）

管理端「用户管理 → 绑卡 → **开始等待刷卡**」，开一个**服务端的绑定窗口**
（`card_bind_sessions`，120 秒）；这期间的某一次刷卡会被服务端解释成
「把这张卡绑给窗口指定的那个人」，而不是去取件。刷卡的那台终端可以是
打印机旁的，也可以是管理员工位上那台「仅用于绑卡」的。

实现在 `kiosk_handlers.go` 的 `tryBindCard`，它**排在认卡之前** ——
要绑的那张卡此刻还没绑过人，按取件那条路走只会得到「工牌未登记」。

- **全局单飞**：同一时刻只允许一个窗口（`card_bind_sessions` 上那条部分唯一
  索引干的）。两个窗口同时开着的话，一次刷卡绑给谁是**不确定**的。
- **卡已绑给别人时不关窗口**，只把原因记在 `error` 列上 —— 管理员换一张卡
  就能接着刷，不必回电脑前重新点一次。浏览器轮询会显示这条原因。
- ⚠️ **小概率错绑**：窗口开着的这两分钟里，若**另一个拿着未绑过卡**的人
  正好来刷，他的卡会被绑给管理员选的那个人。已经绑过卡的人不受影响
  （会被 `ErrCardTaken` 挡下）。缓解是窗口只有 120 秒、全局唯一，
  且管理员的界面会实时显示出绑的卡号，可以立刻解绑重来。
  **把读卡器插在管理员工位上能把这个风险降到几乎没有** —— 别人够不着它。
- 关掉对话框会即时取消窗口；忘了关则 120 秒后自己过期。
  **`closeCardModal` 里那句取消不能删** —— 全局单飞的名字被别人占着时，
  现象是「点开始等待刷卡报已有窗口开着，却找不到在哪儿关」。

#### 路二：把 UID 抄进管理界面（批量发卡时更快）

```
在终端上：  kiosk.py --read      →  刷卡  →  打出 UID
在管理端：  把 UID 粘进「绑卡」输入框 → 确认
```

配合归一，抄错大小写或带上冒号都能对上。**一次绑一批人时用这条** ——
不用为了绑一个人来回走一趟。

如果管理员电脑上另插了一个**键盘模拟读卡器**，直接在那个框里刷也能进
（`frontend/src/utils/cardReader.js` 的兜底监听：焦点不在输入框里时，
把读卡器敲出来的字符捡回来填进去）。

### 终端自检：`/api/kiosk/ping`

终端启动时会打一次 `POST /api/kiosk/ping`（只验 token、不碰任何状态），
把「刷卡没反应」背后那几件长得一样、却要往四个方向修的事分开：
连不上服务器 / 服务端是旧版本 / token 抄错 / 读卡器没读到。

🚫 **自检不能用假卡号去打 `/release`** —— 万一启动那一刻正好有绑定窗口开着，
那张假卡会被绑给一个真人。这是它单独开一个口的原因。

### 一个账号一张卡

`users.card_no` + 部分唯一索引（空串不参与，同 `alipay_open_id` 的模式）。
换卡 = 重新绑（覆盖）。

**一个人要多张卡同时生效**的话这一列不够，得升级成
`user_cards(user_id, card_no UNIQUE)` 的多行表 —— **现在不做**，但扩展路径就是它，
升级时把 `GetUserByCardNo` 改成 JOIN 即可，其余调用点不用动。

## 取件终端

打印机旁一台**树莓派 + USB 读卡器**。终端用 `kiosk_terminals` 表登记，
token 是它的凭据。

### 🔐 这是本系统唯一的无会话写入口

`POST /api/kiosk/release` 挂在 **public 段**（无会话、无 CSRF），认证靠 token。
所以：

- **限流**（`kioskRateAllow`）：卡片号可枚举，不限流等于开了个爆破口。
  与 `login_limiter.go` 的「失败次数」模型不同 —— 枚举时的响应是正常的
  `card_unbound` 而不是失败，所以这里限的是**总次数**。
- **审计日志**：每一次刷卡都留痕，成功与失败都留。
  **无屏幕方案下这是唯一的排障线索** —— 员工说「刷了没反应」时，
  只有这行日志能回答「他到底刷没刷上、服务端当时说了什么」。
- **日志里只打 token 前缀**：它是等价于密码的凭据，而日志经常被整份贴进工单。

安全边界：拿到 token 最多能冒充一台取件终端，而释放仍需一张能刷出卡号的实体卡，
纸也只会从那台物理打印机出来。**卡片可以被克隆**——这是所有刷卡方案的共同弱点，
不是本实现的缺陷；所以绑定/解绑只允许管理员做。

## 硬件

### 无屏幕的代价与补偿

现场那台机器**没有屏幕**。员工看不到失败原因，而四种情况彼此不可互推
（工牌未登记 / 这台没有你的任务 / 打印机离线 / 成功）。→ 用**声码 + 双色灯**：

| 反馈             | 含义                                                   |
| ---------------- | ------------------------------------------------------ |
| 长响 1 声 + 绿灯 | ✅ 任务已开始打印                                      |
| 长响 2 声 + 红灯 | 部分任务失败                                           |
| 长响 3 声 + 红灯 | 全部失败                                               |
| 长响 4 声 + 红灯 | 连不上服务器（**本地**判断，服务端不返回这一档） |
| 短响 2 声 + 红灯 | 这台打印机上没有你的待取件任务                         |
| 短响 3 声 + 红灯 | 工牌未登记，请联系管理员                               |
| 短响 4 声 + 红灯 | 打印机当前不可用，请稍后再试                           |
| 短响 5 声 + 红灯 | 终端未注册或已停用（叫管理员）                         |
| 短响 6 声 + 红灯 | 刷得太频繁                                             |
| 无声             | 误触（空刷），不打扰                                   |

用「长/短」把信号空间分成两半：长响只表示「和打印有关的结果」，
短响只表示「这次刷卡没能进行」。**读卡器旁必须贴一张声码卡** ——
不贴的话没人记得住，等于没有反馈。

> ⚠️ 声码是**降级补偿，不是等价替代**。现场抱怨多的话，加一块 7 寸屏
> 把取件端换成 Chromium kiosk 即可 —— **服务端不用改**（状态码就是接口）。

### 器件

蜂鸣器 + 双色 LED 接 GPIO（`/sys/class/gpio`，只要文件读写、不要第三方库）。
三个引脚号在 `/etc/cups-kiosk.conf` 里配，**全部可选** —— 一个都不配也能用，
只是刷卡没反馈（日志里会明确写一行警告，免得现场以为程序没跑）。

### 读卡器：两类，走两条完全不同的路

|              | **PC/SC**（**推荐**）                | 键盘模拟（HID）                                                                           |
| ------------ | ------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| 例子         | ACR122U、ACR1252                                 | 淘宝几十块的 RFID 读卡器                                                                  |
| 系统接口     | 走`pcscd`，`pcsc_scan` 能验证                | 就是一把 USB 键盘                                                                         |
| 拿到的是     | **规范的 UID**（如 `04A23B1C`）          | 读卡器按自己的格式「敲」出来的字符串                                                      |
| 键盘布局影响 | **没有**                                   | ⚠️**有**：按**键码**输出，机器布局 / NumLock 不同会让同一张卡读出不同字符串 |
| 终端程序     | `scripts/kiosk/kiosk.py`（Python + pyscard）   | `cmd/kiosk`（Go，纯二进制，无运行时应）                                                 |
| 绑定方式     | 终端上`kiosk.py --read` 读出 UID，抄进管理界面 | 管理员电脑上插同型号读卡器，在绑卡框里直接刷                                              |

**推荐 PC/SC** —— 它把「键盘布局」这一整类问题直接消掉了，而 UID 是芯片固化的
唯一标识，稳定、可手抄、可跨机器比对。

⚠️ 用 HID 读卡器的话，`cmd/kiosk/keymap.go` 那张映射表实质上**写死了 US 布局**，
所以树莓派与绑卡那台电脑都必须设成 US，且**必须同型号同配置**。

### 采购前必须先验证

1. **拿一张真工牌放到候选读卡器上读一次**。企业工牌常见 **13.56MHz
   （Mifare/DESFire）**，而廉价读卡器多为 **125kHz（EM4100）** —— **两者不通用**，
   买错了读不出任何东西。
2. 确认读出来的是 UID 而不是厂商自定的格式号。
3. **绑定用的读卡器必须与取件终端同型号** —— 换型号就要重新绑全部卡。

## 部署

### 路线 A：PC/SC 读卡器（推荐，`scripts/kiosk/kiosk.py`）

```bash
sudo apt install pcscd python3-pyscard python3-requests
sudo systemctl enable --now pcscd

# 验证底层通了：刷一张卡，pcsc_scan 里能看到卡
pcsc_scan

# 拿一个终端 token：管理界面「取件终端 → 新增终端 → 配置指引」
sudo cp kiosk.py /usr/local/bin/cups-kiosk && sudo chmod +x /usr/local/bin/cups-kiosk
sudo cups-kiosk --read            # 刷一次卡，把 UID 打出来（绑卡时用）
sudo cups-kiosk                   # 一直跑
```

配置 `/etc/cups-kiosk.conf`（格式与 Go 版一致，两份文档通用）：

```ini
server = http://192.168.1.22:1180
token  = <管理界面「取件终端 → 配置指引」里复制>
device = ACS                    # 可选。多台读卡器时按名字选

# 可选：刷卡后跑一条命令做声光提示（不配就只打日志）。
# $KIOSK_STATUS 是结果码，可以按它决定响几声。
# beep_cmd = /usr/local/bin/beep "$KIOSK_STATUS"
```

⚠️ `chmod 600 /etc/cups-kiosk.conf` —— token 是等同于密码的凭据。

### 路线 B：键盘模拟读卡器（`cmd/kiosk`，Go）

```bash
# 在树莓派上（aarch64 → arm64；armv7l → armv7）
uname -m
scp cups-kiosk-linux-arm64 pi:/tmp/
ssh pi 'sudo /tmp/install.sh /tmp/cups-kiosk-linux-arm64'
```

`scripts/kiosk/install.sh` 会放二进制、装 systemd 单元，并在没有配置时
打印一份模板 + **当前机器的输入设备列表**（`cups-kiosk -list`）——
安装的人照着把读卡器名字填进 `device =`。配置里额外多三个 GPIO 引脚：
`buzzer_pin` / `led_green_pin` / `led_red_pin`（都可选）。

### 自检与权限

`kiosk.py` 启动时会**自检一次**（拿一个不可能存在的卡号打一发），把
「刷卡没反应」背后那几件长得一模一样、却要往四个方向修的事分开：

| 自检结果                       | 说明                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| `✅ 服务器、token、地址都对` | 正常。（内部拿到的是「卡未登记」—— 那正说明前面几关全过了） |
| `连不上服务器`               | 地址/端口错，或网络不通                                       |
| `服务器上还没有取件接口`     | `/api/kiosk/release` 返回 404 —— 服务端跑的还是旧版本     |
| `token 不对`                 | token 抄错（常见：带了首尾空格）                              |

⚠️ `/etc/cups-kiosk.conf` 按建议设成 `600`（token 等同于密码），
**所以普通用户读不了它** —— 要么 `sudo cups-kiosk`，要么
`sudo chown $USER /etc/cups-kiosk.conf`。脚本会把这两条修法直接打出来，
不会让你对着一句 Python traceback 猜。

### 排障

两条路的入口都是日志：

- Python：`journalctl -u cups-kiosk -f`（或直接看它的终端输出）
- Go：`journalctl -u cups-kiosk -f`；`-verbose` 会把每个按键事件也打出来

刷卡后这里会打出结果、失败原因、以及每一条任务的成败。
**员工说「刷了没反应」时，这是唯一的排查入口。**

## 员工侧

- 提交走 `POST /api/pull-orders`（不是 `/api/print` —— 那个在取件模式下 403）。
- 提交页的打印机下拉**只列配有取件终端的**（`/api/printers` 的 `hasKiosk`）。
  少了它，员工能选一台没装终端的机器，任务就进了一个**取不出来也不报错的黑洞**。
  后端 `pullOrderCreateHandler` 有一道同样的校验兜底。
- 「待取件」列表在 `/records` 页顶部，数据源是 `GET /api/pull-orders`
  （查 `print_orders`）。🚫 **不要改成查 `print_jobs`** —— 后者受 `save_history`
  开关影响，关掉时压根不写记录，而「看不到自己待取的任务」恰恰是这个功能
  要解决的问题本身。
- 提交成功后**跳到中间页 `/pending`**（`PendingView.vue`），不是只弹一个 toast。
  员工此刻最想知道的是「**去哪儿、什么时候之前**」，一句飘走的气泡说不下这两件事、
  也留不住。那个页面给的是：大字的打印机名字 + 位置 + 具体的过期时间 + 文件清单。
- 🚫 **`/pending` 与 `/done` 是兄弟但讲的是相反的事**：`/done` 说「钱付了、纸在打」，
  `/pending` 说「纸还没出来，你得去刷卡」。混用会得到「提示已提交打印，员工转身就走」，
  而任务还躺在待取件里。批次号必须从响应里带过去，🚫 不要用「最近一条」去猜。
- 凡是提交路径上会出现「打印成功 / 已提交」这类文案的地方
  （`PrintView` 单/批量、`RecordsView` 重打）都要按响应里的 `held` 分流。
  在取件模式下说「已提交打印」是**谎言**。

## 过期与清理

- `pull_ttl_hours`（默认 72）写进 `print_orders.expires_at`（**复用现有列**）。
  它与 `order_ttl_minutes` 是两回事：后者管「多久内付款」，前者管「员工多久来取」。

### 定时打印被拒绝

`scheduler.go` 绕过订单链路直接 `SendPrintJob`（这条路连计费也绕过了，见 AGENTS.md
的已知缺口）。取件模式下它被**显式拒绝**并写进 `last_error`：让保密文档无人值守地
躺在出纸口，正是拉式打印要消灭的场景。如实报失败而不是静默跳过 ——
后者会让用户以为任务跑过了。

- `expireHeldOrders` 每 30 秒扫一次，**先迁移状态、后删文件**。
  顺序不能反：先删文件的话，员工若正好在这一刻刷卡，领到的是一条文件已经
  不在的订单 —— 而员工什么错都没犯。
- 员工可以主动撤销（`DELETE /api/pull-orders/{id}`，仅限本人、仅限 `held`）。

## 风险

| 风险                                                    | 说明                                                                                                                                                                                                                             |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **卡号跨读卡器不一致**                            | 最大的功能性风险。缓解只有「统一读卡器型号/配置/键盘布局」。多卡多格式需要升级成`user_cards` 表                                                                                                                                |
| **无屏幕的信息损失**                              | 声码只能传两三个 bit。靠审计日志 + 管理端可见的终端状态兜底                                                                                                                                                                      |
| **`ListActiveOrderFiles` 漏状态**               | 后果是静默删文件。已用测试钉住（验证过它会红）                                                                                                                                                                                   |
| **`reconcilePrintingOrder` 的 pull 翻译漏分支** | 后果是「释放失败 → 走退款路径 → 任务标 failed」或「卡 printing 永不回收」                                                                                                                                                      |
| **单次释放的数量与超时**                          | N 个任务同步送印，`Server.WriteTimeout=120s` 是硬顶。任务特别多时需要调参                                                                                                                                                      |
| **两套终端程序并存**                              | `scripts/kiosk/kiosk.py`（PC/SC）与 `cmd/kiosk`（HID）做的是同一件事的两种读卡方式。**标准型号之后应当删掉用不上的那个** —— 两份实现各自演化的话，「改了一边忘了另一边」迟早发生，而现象是「某种读卡器上刷卡没反应」 |
