# 微信支付：为什么还没接入

> **一句话**：能接，但门槛在**资质与备案**，不在代码。
>
> 本项目目前只有支付宝与余额两种支付方式。微信支付只留了占位（渠道常量、前端 logo、文案），没有协议实现 —— 这是有意的，不是遗漏。

## 现状

| 项 | 状态 |
| --- | --- |
| 支付方式列表 | 只有「余额」和「支付宝」。微信**不会出现**在列表里 |
| 接口 | `POST /api/orders/batch/{id}/pay` 传 `method=wechat` 会返回 **400「该支付方式当前不可用」** |
| 前端 | `PAY_LOGOS.wechat`、`payProviderName`、`providerLabels.wechat` 等占位都在，logo 也备好了 |
| 后端 | `internal/payment` 里没有微信实现；`buildProvider("wechat")` 恒返回「不可用」 |

之所以**不把微信列进支付方式**，是为了避免「点了必然失败」的按钮：列表里出现什么，就必须真能付。

## 为什么没接：三道门

### 1. 主体资质 —— 个人申请不了

微信支付商户号**必须**用营业执照/登记证书申请。官方支持的入驻主体只有这几类：

- 企业（合资、独资、国有、私营、有限责任等）
- 企业分支机构、合伙企业、其他企业
- 外国企业常驻代表机构
- 个体工商户

**没有「个人」这个选项。** 再看支付宝：个人实名账号就能签「手机网站支付 + 电脑网站支付」，这也是本项目先做支付宝的直接原因之一。

### 2. 域名备案 —— 绕不过去

- **H5 支付**：支付域名必须完成 ICP 备案，申请时要**提交备案截图**；一级域名必须公网可访问、能看到具体经营内容；最多添加 5 个域名。备案主体与商户号主体不一致时，只接受「同集团 / 品牌与经销商 / SaaS 服务」三种合作关系，还要提供授权函。
- **Native 支付**：新商户入驻时选「PC 网站」经营场景，要填 PC 网站域名（同样需备案）和网站授权函。
- **JSAPI**：回调域名需备案，还要配置「支付授权目录」，与实际支付页面目录一致。

⚠️ **重要**：「本项目结算走主动查单、不发回调」**绕不过备案**。备案要求出现在**开通产品权限的审核环节**，是「你能不能拿到这个权限」的问题，跟运行时用不用回调没有关系。

### 3. 产品审核 —— 按工作日算

每个产品都要在商户平台单独申请：

| 环节 | 官方说明 |
| --- | --- |
| Native / H5 / JSAPI 权限 | 审核 **7 个工作日**内 |
| H5 支付域名配置 | 审核 **3–5 个工作日**，通过后约 10 分钟生效 |

也就是说，即使资质齐全，从提交到能联调也要一到两周。

## 三种收款方式怎么选

| 产品 | 用户怎么付 | 官方申请要求 | 对本项目的适配 |
| --- | --- | --- | --- |
| **Native（PC 扫码）** | 页面显示二维码，用户用微信扫 | 已有商户号 → 产品中心开通；新商户选「PC 网站」场景，填网站授权函与备案域名；审核 7 个工作日 | **最合适**。服务端出站下单拿 `code_url`，二维码渲染在我们自己的页面上，不涉及跳转域名校验 |
| **H5 支付** | 手机浏览器跳到微信支付 | 支付域名须 ICP 备案（提交截图）、一级域名公网可访问、最多 5 个；审核 7 工作日 + 域名配置 3–5 工作日 | 可行，但**成本最高**：要备案域名，且微信会校验来源域名 |
| **JSAPI 支付** | 在**微信内部浏览器**里拉起 | 必须**已认证服务号**（订阅号、未认证公众号不支持），认证主体须与商户号一致；绑定 AppID、配置支付授权目录；审核 7 个工作日 | **不适合**。顾客是扫码或用普通浏览器进来的，不在微信里 |

## 一个绕不开的体验问题：手机上扫不了自己的屏幕

Native 支付把二维码显示在页面上。**电脑端没问题**（手机扫电脑屏幕），但**手机端顾客没法扫自己屏幕上的码**。

两种处理方式：

1. **手机端不提供微信**，只留支付宝与余额；微信只在电脑端出现。
   最稳，零风险，代价是手机用户用不了微信。
2. 尝试用 `weixin://` 这类 scheme 从浏览器直接唤起微信。
   ⚠️ 微信对外部浏览器唤起的态度、以及各版本行为是否一致，**必须真机验证**；不要照抄本项目支付宝那套 `alipays://` 的经验 —— 两者不是一回事。

## 真要接入时，需要准备什么

**凭据**（都在商户平台获取）：

- 商户号 `MCHID`
- 与商户号绑定的 AppID（服务号 / 小程序 / 移动应用，按产品而定）
- APIv3 密钥
- 商户 API 证书与私钥
- 微信支付公钥（用于验签）

**接口版本**：微信支付 **APIv3**（不是老的 V2）。

**基本流程**：

```
服务端下单 → 拿到 code_url
  → 前端把 code_url 渲染成二维码
  → 用户扫码付款
  → 服务端主动查单确认到账（不必依赖回调）
```

结算方式与支付宝那条路一致：**主动查单**。本项目在没有公网回调的情况下也能正常结算，微信同样适用。

**费率**：标准费率 0.6%（按行业类目可能不同，以商户平台为准）。

## 开发者：代码接入位置

| 位置 | 要做什么 |
| --- | --- |
| `internal/payment/` | 新增微信 provider，实现 `Provider` 的七个方法 |
| `cmd/server/payment.go` 的 `buildProvider` | 把 `wechat` 分支从「恒不可用」改成「配置齐全才构建」 |
| `availableProviders()` | 判定要与支付宝**同构**（配置缺任何一项就不列出） |
| `cmd/server/payment_test.go` | 现有两条测试会拦住「微信被列出来」和「分支不再返回不可用」，接入时一并更新 |
| 前端 | logo 与文案已就绪，把渠道放出来即可 |

⚠️ **接口抽象是按支付宝的词汇抽的**：`Request.Channel` 的 `wap` / `page` / `qrcode` 分别对应支付宝的手机网站支付 / 电脑网站支付 / 当面付。微信的 Native / H5 / JSAPI 与它不是一一对应，接入时先想清楚这三个值怎么映射。

⚠️ **签名实现要有外部期望值**。本项目在支付宝上吃过一次亏：假网关和被测代码犯了同一个错（都漏排 `sign_type`），42 个用例全绿，直到真实沙箱回 `isv.invalid-signature` 才发现。微信这条也一样 —— 签名函数必须拿**官方算例或真机报文**当期望值，不能凭印象写测试。

## 和支付宝的对比

| | 支付宝 | 微信支付 |
| --- | --- | --- |
| 个人主体 | ✅ 个人实名账号可签手机/电脑网站支付 | ❌ 必须营业执照 |
| 域名备案 | 不校验（回调地址可用内网 IP） | 支付域名 / 回调域名需 ICP 备案 |
| 手机端体验 | 手机网站支付，付完自动跳回 | H5 需备案；Native 在手机上扫不了自己的屏幕 |
| 本项目状态 | ✅ 已完整实现 | ⬜ 仅占位 |
