## 必须先定的：用哪种收款产品

**这个决定排在协议细节之前**，因为它决定的不只是「调哪个接口」，而是整套交互：

| 产品 | 交互 | 已知门槛（待确认） |
| --- | --- | --- |
| **Native 支付** | 服务端出单拿二维码内容，**渲染在我们页面上**，用户用微信扫 | 申请时需「PC 网站」经营场景，要已认证服务号/公众号 + 已备案域名 |
| **H5 支付** | 手机浏览器跳转 / 唤起微信 | 需单独申请；H5 域名必须**已 ICP 备案**，且会校验来源 |
| **JSAPI 支付** | 微信内置浏览器内拉起 | 需公众号 + openid（要走 OAuth），用户得在微信里打开我们的页面 |

### 对本项目的判断（待确认，但方向明确）

本项目典型形态是**内网单容器**（`192.168.x.x`，无公网域名）。据此：

- **H5 支付基本不可行。** 它要求 H5 域名已备案并校验来源，内网 IP 填不进去。
- **Native 支付可行。** 服务端只是**出站**调 API + 主动查单，二维码渲染在我们自己的页面上 —— 位置无关。
- **JSAPI 不可行。** 用户是在普通手机浏览器里访问这个内网地址，不是在微信里。

### 一条容易搞错的因果（已核实）

「本项目不用回调、结算走主动查单」**绕不过资质的门槛**。
支付宝那条路压根不发 `notify_url`，所以「回调地址必须是备案域名、不支持 IP」这条**确实**卡不到我们。
但微信的备案要求出现在**开通产品权限的审核环节**，不是运行时约束 —— 它是「你能不能拿到这个权限」的问题，与我们的架构无关。

## 内网下的体验缺口（待确认）

若走 Native，则**手机上无法扫自己屏幕上的二维码**。可能的出路：

1. 用 `weixin://wxpay/bizpayurl?pr=…` 这类 scheme 从当前浏览器直接唤起微信。
   ⚠️ 这条路**未经核实**，微信是否放行外部浏览器唤起、以及各版本行为是否一致，
   必须**真机验证**。别照抄 `PaymentPanel.vue` 里支付宝那套 `alipays://` 的结论。
2. 手机上不提供微信（只留支付宝与余额），微信只在电脑端出现。
   最保守，零风险，但手机用户用不了微信。

⚠️ 注意 `PaymentPanel.vue` 里「唤起 App」那个按钮**不是必然存在的**：
若走 Native（页内扫码），手机上压根没有「唤起」这个动作，该讨论的是这个按钮
是否还留着，而不是「换成微信的 scheme」。

## 接口适配问题（比协议更早要回答）

`payment.Provider` 的七个方法
（`Name` / `Create` / `Query` / `Refund` / `Close` / `VerifyCallback` / `CallbackAck`）
是照支付宝抽出来的。接入微信时先回答：

1. **`Request.Channel` 的三个常量够不够用？** `qrcode` / `wap` / `page` 是
   **支付宝产品形态的词汇表**（当面付预下单 / 手机网站支付 / 电脑网站支付），
   微信的收款方式与它不是一一对应。
2. **`VerifyCallback` 要不要实现？** 内网部署、结算靠主动查单，支付宝那条路
   不实现回调也跑得好好的。
3. **`Close` / `Refund` 语义是否一致？** 比如退款是否需要额外的证书/权限。

⚠️ 这几条是**纯接口问题，与协议无关**，所以它们现在就写得下来 ——
而它们恰恰是接入里唯一真正有风险的部分。**别让一个「全方法返回未实现」的
stub provider 把它们掩盖成「已解决」。**

## 为什么先不写签名

因为**缺的不是「通用性」，是 oracle**。

本仓库被烧过一次，记录在 `internal/payment/alipay_test.go`：

> 这个假网关当初就是和被测代码犯了同一个错（都排除 `sign_type`）才让 42 个
> 用例全绿，直到真实沙箱指出 `isv.invalid-signature`。别再改回去。

**42 个用例全绿，全是错的。** 那不是覆盖率不够，而是**测试与被测代码共享了
同一个误解，于是互相作证**。

支付宝那套之所以最终能写对，是因为它有 oracle —— 沙箱报
`isv.invalid-signature` 时会把**实际使用的验签串回显出来**，
`TestAlipayRequestSignContent_MatchesGateway` 就是拿那段回显当期望值。

所以接入微信的**第一件事不是写 `wechat_sign.go`，而是搞到一条外部来的测试向量**
（给定这份待签材料，签名/密文应当是这些字节）。有了它，签名函数就是
「写出来让它满足一个外部期望」，同时变得可写、可测。

同理，`verify-alipay.sh` + `fake-alipay-gateway.js`（照真协议实现的假网关，
无需商户资质即可端到端跑）是接入微信时**最值得投入的基础设施** ——
但它必须等协议确定之后写，现在写等于写一份我的猜测的假协议。

## 绊线测试（已核实会真的失败）

`cmd/server/payment_test.go` 两条，都实测过「把它该拦的东西放进去就会红」：

| 测试 | 拦什么 |
| --- | --- |
| `TestWechatBranchStaysUnavailable` | 微信分支不再返回 `ErrUnavailable`。守的是 HTTP 状态码行为（见下） |
| `TestWechatNotAdvertised` | 微信出现在支付方式列表里。**覆盖面窄**，见它自己的注释 |

### 为什么守着 `ErrUnavailable` 这个具体哨兵

渠道名**没有白名单校验**（`order_print.go` 与 `billing_handlers.go` 都直接取
请求体里的 `method`/`provider`），所以客户端今天就能 POST `{"method":"wechat"}`。
`ErrUnavailable` 让四处行为保持可诊断：

| 路径 | 维持现状 | 换成别的哨兵 / 返回 stub 实例 |
| --- | --- | --- |
| `writePaymentStartError` | **400**「该支付方式当前不可用」 | **502 + 内部错误原文**（default 分支） |
| 查单 handler | 400 | 502 |
| 回调 handler | **404**「unknown provider」 | 400 bad signature |
| `closePreviousBatchPayment` | 静默跳过 | 每次刷新一条无意义的错误日志 |

这四处**恰好只在「有人手工构造了一个不可能成功的请求」时可达** ——
也就是最需要诊断信息的时候。
